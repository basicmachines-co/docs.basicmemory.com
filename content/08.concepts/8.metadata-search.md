title: Metadata Search
description: Filter and find notes by their YAML frontmatter — status, type, tags, priority, confidence, custom fields, and more.
---

Every note in Basic Memory has YAML frontmatter at the top. Metadata search lets you find notes by those fields — status, type, tags, custom fields, anything you put there. It's how you ask things like _"show me all in-progress specs tagged security"_ or _"find decisions made in the last quarter with priority high or critical"_ without scanning text.

::docs-video{src="/videos/docs-metadata-search.mp4" poster="/videos/posters/docs-metadata-search.png" alt="Filtering notes by frontmatter fields in Structured search"}
::

Metadata search is a parameter on the same [`bm_search`](/reference/mcp-tools-reference#bm_search) tool you use for text and [semantic search](/concepts/semantic-search). You can use it on its own, or combine it with a text query and tag filters.

::tip
Frontmatter is structured data. The richer your frontmatter, the sharper your search. A note with `type: meeting`, `status: open`, `priority: high`, and `attendees: [...]` is reachable from many more angles than one with just a title.
::

::note
Observation categories such as `[decision]`, `[rule]`, or `[follow-up]` are not frontmatter fields — see [Searching observations by category](#searching-observations-by-category) below instead of `filters`.
::

---

## What's in your frontmatter

Anything you put in the YAML block at the top of a note becomes searchable:

```markdown
---
title: Auth Design
type: spec
tags: [security, oauth]
status: in-progress
priority: high
confidence: 0.85
---
```

Use `filters` for tags, status, and custom fields; `note_types` filters note types. You can also reach into nested objects with **dot notation** — `schema.confidence` targets the `confidence` key inside a `schema` object.

::note
Field **names** must match the chars `A-Z a-z 0-9 _ -` (with `.` for nesting). Field **values** can be strings, numbers, booleans, dates, or lists.
::

---

## Filter syntax

`filters` is a JSON object. Each key is a field name; each value is either a literal (for equality) or an operator object.

Multiple top-level keys combine with **AND** — all conditions must match.

### Equality

```json
{"status": "in-progress"}
```

### Array contains (all values present)

For list-valued fields like `tags`, an array means _"all of these"_:

```json
{"tags": ["security", "oauth"]}
```

### `$in` — any of

Match if the field equals **any** value in the list. This is how you express OR within a single field:

```json
{"priority": {"$in": ["high", "critical"]}}
```

### Comparison — `$gt`, `$gte`, `$lt`, `$lte`

Numeric or lexicographic comparison; boundaries on `$gte`/`$lte` are inclusive.

```json
{"confidence": {"$gt": 0.7}}
{"score": {"$lte": 100}}
```

### `$between` — inclusive range

Both ends included; the value must be exactly two items:

```json
{"confidence": {"$between": [0.5, 0.9]}}
```

### Several operators on one field

Operators in one object AND together, so a range can be written the way you'd write it in MongoDB:

```json
{"started": {"$gte": "2026-01-01", "$lt": "2026-02-01"}}
```

### `$contains` — array contains

The operator form of the array filter above. Takes one value or a list, all of which must be present:

```json
{"tags": {"$contains": "security"}}
{"tags": {"$contains": ["security", "oauth"]}}
```

### `$exists` and null — present or missing

`$exists: true` matches notes that have a non-null value at that key; `$exists: false` matches notes where it's missing or null. Equality with `null` is the same as `$exists: false`:

```json
{"owner": {"$exists": true}}
{"owner": null}
```

### Nested fields (dot notation)

```json
{"schema.confidence": {"$gt": 0.7}}
```

### Operator spelling

The leading `$` is optional: `{"priority": {"in": ["high"]}}` and `{"confidence": {"gte": 0.7}}` work the same as `$in` and `$gte`. An unknown operator is refused with a list of the valid ones.

### Operator reference

| Operator | Value | Behavior |
|----------|-------|----------|
| _(scalar)_ | string / number / bool / date | Exact match |
| _(array)_ | list of scalars | All values must be present (for list fields) |
| `$in` | non-empty list | Any of |
| `$gt`, `$gte`, `$lt`, `$lte` | number or string | Comparison (gte/lte inclusive); strings compare lexicographically — dates as ISO strings |
| `$between` | `[min, max]` | Inclusive range, exactly 2 values |
| `$contains` | value or non-empty list | All values present in a list field |
| `$exists` | `true` / `false` | Has a non-null value / is missing or null |
| _(null)_ | `null` | Missing or explicitly null (same as `$exists: false`) |

::note
Several operators in one object AND together (`{"$gt": 0.5, "$lt": 1.0}`), and the `$` prefix is optional. These shapes were added in [v0.24](/whats-new/v0-24); earlier versions allowed one operator per field and required the `$`. There's no `$ne`, `$nin`, or `$regex`; combine multiple top-level keys with AND, and use `$in` for OR within a field. `null` is accepted only as an equality value, not inside `$in`, `$between`, comparisons, or lists.
::

## Tags and note types

Use `filters={"tags": ["security"], "status": "draft"}` for frontmatter fields and `note_types=["spec", "decision"]` for note types. The old top-level `tags` and `status` MCP parameters are removed.

```python
bm_search(filters={"tags": ["security", "oauth"]})
bm_search(note_types=["spec", "decision"], filters={"status": "draft"})
```

## Combining with text and semantic search

Metadata filters compose with everything else `bm_search` does. The text query and the filters apply together (AND):

```python
# OAuth-related notes that are still in progress
bm_search("OAuth", filters={"status": "in-progress"})

# Pure metadata — no text query
bm_search(filters={"type": "spec", "status": "active"})

# Text + tag shortcut + metadata
bm_search("auth", filters={"tags": ["security"], "priority": {"$in": ["high", "critical"]}})
```

See [Semantic Search](/concepts/semantic-search) for how text and vector modes interact.

## From the CLI

The CLI retains its command names and shortcut flags:

```bash
# Simple equality
bm tool search-notes "" --meta status=draft

# Multiple --meta flags AND together
bm tool search-notes "" --meta status=active --meta priority=high

# Full JSON filter
bm tool search-notes "" --filter '{"confidence": {"$between": [0.3, 0.8]}}'

# Convenience shortcuts
bm tool search-notes "auth" --tag security --tag oauth --status draft --type spec
```

See [CLI Reference](/reference/cli-reference#bm-tool-search-notes) for every flag.

## Worked examples

Given a few notes like this:

```markdown
---
title: Auth Design
type: spec
status: in-progress
priority: high
tags: [security, oauth]
confidence: 0.85
---
```

```markdown
---
title: Search Redesign
type: spec
status: planning
priority: medium
tags: [search, performance]
confidence: 0.6
---
```

| You want… | `filters` |
|-----------|--------------------|
| All in-progress specs | `{"status": "in-progress", "type": "spec"}` |
| Specs with confidence above 0.7 | `{"type": "spec", "confidence": {"$gt": 0.7}}` |
| Anything high or critical priority | `{"priority": {"$in": ["high", "critical"]}}` |
| Specs in confidence range [0.5, 0.9] | `{"type": "spec", "confidence": {"$between": [0.5, 0.9]}}` |
| Decisions since April | `{"type": "decision", "date": {"$gte": "2026-04-01"}}` — dates compare as ISO strings |
| Notes tagged both `security` AND `oauth` | `{"tags": ["security", "oauth"]}` |
| "OAuth" matches in still-open work | use `bm_search("OAuth", filters={"status": "in-progress"})` |
| Anything with nested `schema.confidence` ≥ 0.7 | `{"schema.confidence": {"$gte": 0.7}}` |

## Searching observations by category

Observation categories (`- [decision] ...`, `- [rule] ...`) live on observations, not in frontmatter — so they get their own filter, `categories`, instead of `filters`:

```python
# All decision observations, anywhere
bm_search(categories=["decision"])

# Decisions mentioning auth
bm_search("auth", categories=["decision"], items=["observation"])
```

Matching is exact, and when you pass `categories` without `items`, results default to observations. From the CLI:

```bash
bm tool search-notes "auth" --entity-type observation --category decision
```

## Searching by valid time

Frontmatter dates such as `date` or `due_date` describe a whole note. When individual facts have their own dates, put the date on the observation with a valid-time qualifier (new in [v0.24](/whats-new/v0-24)):

```markdown
- [decision] @effective[2026-06-10,2026-07-27) Cache layer uses Redis.
- [decision] @effective:2026-07-27 Cache layer uses Memcached.
```

`bm_search` has three filters for that authored time. They're about what the note *says* was true, separate from `since`, which filters by when content was indexed:

| Parameter | Value | Matches |
|---|---|---|
| `valid_at` | A date (`"2026-07-01"`) or an instant (`"2026-07-01T09:00:00Z"`) | Observations whose valid range contains it |
| `valid_overlaps` | A range literal: `"[2026-06-01,2026-07-01)"`, `"(,2026-07-27]"`, `"[2026-06-10,)"` | Observations whose valid range overlaps it |
| `time_kind` | `effective`, `valid`, `occurred`, `due`, or `mentioned` | Only that kind of qualifier; works on its own too |

```python
# What cache decision was in effect on July 1st?
bm_search("cache", valid_at="2026-07-01", time_kind="effective")

# Everything due during Q3
bm_search(valid_overlaps="[2026-07-01,2026-10-01)", time_kind="due")
```

- `valid_at` and `valid_overlaps` can't be combined in one search.
- Observations without a qualifier are excluded from any valid-time search — an undated fact makes no claim about when it holds. Drop the filter to search dated and undated content together.
- Results are observation-level, each carrying the assertion that matched, because one note can hold several dated facts that disagree.
- Calendar dates and instants are separate: a date query matches date ranges, an instant query matches instant ranges. A timestamp without an offset is read as UTC.
- A malformed filter is refused with an error rather than ignored.
- Valid-time filters compose with text, vector, hybrid, and metadata filters.
- These filters are MCP and API parameters; `bm tool search-notes` doesn't have flags for them.

The authoring syntax is covered in [Observations and Relations](/concepts/observations-and-relations#when-a-fact-holds-valid-time).

## Type handling

- **Strings** match exactly (case-sensitive).
- **Numbers** — comparison operators detect numeric values automatically, so `"0.5"` and `0.5` compare the same way.
- **Booleans** are compared as the strings `"True"` and `"False"`.
- **Dates and datetimes** are normalized to ISO strings.
- **Missing fields** don't match equality, comparison, or list filters. To find notes that lack a field, use `{"field": null}` or `{"field": {"$exists": false}}`.

---

## Limits and caveats

- **AND only at the top level.** Combine multiple keys to AND; use `$in` for OR within a single field. There's no top-level `$or`.
- **No full-text matching inside metadata.** Use exact, range, or `$in` matching — for free-text search across note bodies, use [text or semantic search](/concepts/semantic-search).
- **Lists in filters must be non-empty.** `{"tags": []}` is rejected.
- **`$between` requires exactly two values.**
- **No `$ne`, `$nin`, `$regex`.** They're not in the operator set.
- **Markdown notes only.** Non-Markdown files (PDFs, images) aren't matched by metadata filters.
