Connecting Basic Memory over MCP gives your assistant the tools. It doesn't teach it *when* to reach for them. A few standing instructions are the difference between an assistant that occasionally writes a note and one that actually maintains your knowledge base — searching before it answers, capturing decisions as they happen, and linking new notes into the graph.

There are three ways to give those instructions, from least to most effort.

---

## 1. Install Agent Skills (recommended)

[Agent Skills](/integrations/skills) are packaged instructions that teach agents Basic Memory best practices — the note format, when to capture, how to search and resume work, schema workflows, and knowledge-base maintenance. If your client supports skills, this replaces hand-written guidance:

- **Claude** (claude.ai and Claude Desktop) and **ChatGPT**: download the combined skill, `basic-memory.zip` for Claude or `basic-memory-chatgpt.zip` for ChatGPT, and upload it. The [Agent Skills guide](/integrations/skills) has the download links and where to upload.
- **Coding agents** (Claude Code, Codex, Cursor, and others): install from the terminal.

```bash
npx skills add basicmachines-co/basic-memory/skills -g
```

That installs the full set for your user account. To start smaller, add just one: `npx skills add basicmachines-co/basic-memory/skills --skill memory-notes -g` (the core note-writing skill), and add others as you need them.

---

## 2. Add project-level instructions

If you'd rather write your own guidance — or your client doesn't support skills — put it where your assistant reads standing instructions:

- **Claude Projects** — in Claude (web or desktop), open your project's settings and paste your guidance into the **project instructions**. Every conversation in that project starts with it.
- **Claude Code** — add it to the repo's `CLAUDE.md`. Claude Code loads it automatically in that repository.
- **Codex and other coding agents** — add it to `AGENTS.md` in the repo root, the convention most coding agents read.
- **Other clients** — use the custom-instructions or system-prompt field your client provides.

### A starting instruction block

Paste this and adapt it to your workflow:

```markdown
## Basic Memory

You have persistent memory through Basic Memory's MCP tools.

- Before answering questions about prior work or decisions, search first:
  `search_notes`, then `build_context` on relevant `memory://` URLs.
- Capture important decisions, findings, and context as notes with
  `write_note` during the conversation — don't wait to be asked.
- Structure notes semantically: observations as `- [category] fact #tag`
  and relations as `- relates_to [[Other Note]]`. Use exact titles of
  existing notes in wikilinks so they resolve.
- Update existing notes with `edit_note` instead of creating duplicates.
  If `write_note` reports "Similar existing notes", decide whether to merge
  into one of them, link them, or keep the new note.
- Calls without `project` use the default project (the POSIX tools refuse
  unqualified paths when several projects exist). If the target project is
  ambiguous, ask once, then pass `project` on every call.
- For quick navigation, use `ls`, `find`, `grep`, and `cat` (sections and
  line ranges keep reads small). Read a tool's manual page
  (`memory://man/<tool>(3)`) when a call fails or its use is unclear.
- A refused write is a tool error and nothing was written. Read the error
  before retrying.
```

::note
Want more to work from? The [extended AI assistant guide](https://github.com/basicmachines-co/basic-memory/blob/main/docs/ai-assistant-guide-extended.md) is a full instruction document you can download and customize. A [condensed version](https://github.com/basicmachines-co/basic-memory/blob/main/src/basic_memory/mcp/resources/ai_assistant_guide.md) ships inside Basic Memory as the `memory://ai_assistant_guide` resource, and the built-in manual serves a page per tool at `memory://man`.
::

## 3. Say it in the conversation

Instructions don't have to be configured up front. Basic Memory is designed so you can direct it naturally as you work:

```text
"Make sure you add observations and relations to this note."
"Search my notes before answering — what did we decide about auth?"
"Record this decision in Basic Memory."
```

Your assistant can even write a note about *how you like your notes* — and find it again in the next conversation.

::tip
**Using your tool's built-in memory too?** There's a paste-once routing rule that teaches the agent to treat built-in memory as the short-term cache and Basic Memory as the long-term store — see [Using Basic Memory with Built-in AI Memory](/concepts/vs-built-in-memory).
::

---

## What good usage looks like

- **Search before answering.** Questions like "what did we decide about X?" should trigger `search_notes`, not a guess from the conversation so far.
- **Capture as you go.** Decisions, requirements, and findings get recorded when they happen, structured with observations and relations.
- **Build context on follow-ups.** `build_context` with a `memory://` URL pulls in a note *and* its connected notes, so continuation conversations start warm.
- **Edit, don't duplicate.** Existing notes grow with `edit_note`; new notes link back to what they extend. When `write_note` flags similar existing notes, that's the cue to merge or link.
- **Read only what you need.** `search_notes(compact=True)` and `build_context(compact=True)` return identifiers without bodies so the agent can pick what to open. `cat` reads one section, a line range, or a token budget instead of a whole note.
- **Name the project.** There's no session "active project" — a call without `project` goes to the default project. With several projects, pass `project` or use project-qualified paths like `research/notes/topic.md`.

## What changed for assistants in v0.24

If you wrote instructions for an earlier version, a few behaviors are worth updating:

- **POSIX read tools are on by default.** Assistants now see `ls`, `find`, `grep`, `cat`, `tail`, and `man` next to the rich tools. Projects act as mount points: `ls(path="/")` lists them, and a path starting with a project name routes there. Set `enable_posix_tools=false` to hide them.
- **Refusals are tool errors.** A refused `write_note`, `edit_note`, `delete_note`, or `move_note` comes back with `isError` set, never as an ordinary result. Nothing is written when a call is refused.
- **Guard concurrent edits.** Pass `expected_checksum` (the `checksum` from a JSON `read_note`, `write_note`, or `edit_note` result) to `edit_note`, or to `write_note` with `overwrite=True`, so a write only lands on the revision the assistant read. A conflict returns `NOTE_REVISION_CONFLICT` with the current checksum; `read_note(include_content=False)` refreshes it cheaply.
- **`replace_section` needs the exact heading.** It fails instead of appending a duplicate section when the heading is missing.
- **`grep` matches keywords.** A pattern found in no note returns nothing. Pass `semantic=True` to rank by meaning.
- **The manual is built in.** `memory://man` lists a page per tool, and notes themselves are readable as resources at `memory://<project>/<path>`.

::tip
A one-line instruction like "Read `memory://man` before using an unfamiliar Basic Memory tool" goes a long way: each page has verified examples and the common mistakes for that tool.
::
