Projects are how a team organizes its knowledge base. Every project in a team workspace has a visibility, and every member's access follows their [role](/teams/members-and-roles).

---

## Project visibility

Team projects come in two visibilities. The right one depends on who needs to see the work:

| Visibility | Who can see it | When to use |
|------------|----------------|-------------|
| **Standard** (`workspace`) — _default_ | Everyone in the team, based on their team role | Most team work — the open, shared knowledge base |
| **Shared** (`shared`) | Only people you grant access to, each with **view** or **edit** access | Sensitive topics (hiring, contracts, security audits) where you want a controlled group |

When you create a cloud project, you can set its visibility from the CLI:

```bash
# Standard — visible to everyone in the team workspace (default)
bm project add team-wiki --cloud --workspace acme --visibility workspace

# Shared — only people you grant access to
bm project add hiring-2026 --cloud --workspace acme --visibility shared
```

::note
`--visibility private` is refused as of v0.24. The cloud has only `workspace` and `shared` visibility, and older CLIs that accepted `private` created a team-visible project while reporting success. For a project only you can see, create a `shared` project and don't grant anyone else access, or keep the project in your personal workspace.
::

See the [CLI Reference](/reference/cli-reference) for full `bm project add` options.

## Working with team projects

Once you're part of a team, projects show up everywhere you work:

- **In the app** — Select the project in the sidebar.
- **In your AI assistant (MCP)** — your assistant's project list spans every cloud workspace you can access, so it reaches team projects without extra setup.
- **In the CLI** — `bm project list` shows projects across all your workspaces. As of v0.24, a team project with a local sync path is listed as syncable rather than `cloud-only`.

### Syncing team projects with local files

`bm cloud pull` and `bm cloud push` are the sync workflow for team projects. They are additive (never delete on the destination), authorized per project — read access to `pull`, edit access to `push` — and need no `bm cloud setup`. In v0.24 they list the project in one request and transfer eight files at a time, so large team projects sync much faster.

```bash
bm cloud sync-setup team-wiki ~/team-wiki
bm cloud pull --name team-wiki
bm cloud push --name team-wiki
```

The deprecated `bm cloud sync` and `bm cloud bisync` mirror commands exit on team workspaces with a notice pointing at `pull`/`push`. See [Cloud Sync](/cloud/cloud-sync).

### Removing a team project

`bm project remove <name> --cloud` permanently deletes the project's cloud files for everyone in the team — there is no keep-files option. The CLI asks for confirmation and reminds you that deleted files can be recovered only from a snapshot (`bm cloud snapshot list`). See [Remove a Cloud Project](/cloud/cloud-guide#remove-a-cloud-project-and-its-data).

### Workspace commands

```bash
# List the cloud workspaces available to you
bm cloud workspace list

# Set the default workspace for CLI and MCP routing
bm cloud workspace set-default acme
```

You can also target a specific workspace when creating a project, either from the CLI (`--workspace`) or from MCP (`create_memory_project(workspace="acme")`).

### Targeting a team project explicitly

If a project name exists in more than one workspace (say, `research` in both your personal and team workspaces), resolution prefers your default workspace — or asks you to disambiguate. To be explicit, use a **workspace-qualified memory URL**:

```text
memory://acme/research/architecture-decisions
```

The form is `memory://<workspace-slug>/<project>/<path>`. From the CLI, pass `--workspace` on the command instead.

## Bringing existing notes into a team project

When you join (or start) a team, you'll often want to promote work from your personal workspace into the shared one. Cross-workspace transfers are a **copy** workflow — export from the source, import into the target, verify, then optionally delete the original.

See [Copy Content Between Workspaces](/teams/copy-between-workspaces) for the project ZIP, single-note, MCP, and local-sync workflows, along with caveats around wikilinks, permissions, and share links.
